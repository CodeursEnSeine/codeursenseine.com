Les code reviews sont censées améliorer la qualité du code.

Alors pourquoi se transforment-elles si souvent en débats interminables sur du nommage ou du formatage… pendant que les vrais enjeux passent à côté ?

Dans beaucoup d’équipes, les Pull Requests se concentrent sur le visible et le facile à commenter. Pendant ce temps, les aspects les plus structurants (architecture, maintenabilité, dette implicite) sont peu discutés voire ignorés.

Le problème n’est pas un manque de compétence.
C’est un manque de cadre pour décider ce qui compte vraiment.

Comment distinguer ce qui doit bloquer une PR de ce qui relève d’une simple préférence ?
Comment maintenir un haut niveau d’exigence sans créer de friction permanente ?

Dans cette conférence, je propose une grille simple et pragmatique pour classer les commentaires en quatre catégories : bloquant, structurant, amélioration, préférence.

À partir d’exemples concrets et d’exercices interactifs, nous verrons comment :
- réduire les débats inutiles
- focaliser les discussions sur l’essentiel
- et transformer la review en outil de progression collective

Car l’objectif d’une review n’est pas de tout corriger. Mais de corriger ce qui compte.
